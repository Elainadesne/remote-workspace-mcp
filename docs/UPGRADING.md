# 升级与回退

`upgrade_bridge.py` 仅提供升级指引：执行后给出提示并退出 2，不会覆盖文件、生成配置、启动服务或读取会话。本项目使用可审阅的源码目录升级流程，不提供自动升级器。

推荐使用并排目录升级：

1. 记录目前运行的桥接、Python、Codex、tunnel-client 版本和启动命令；把私有配置保存在源码之外
2. 从可信仓库取得指定版本的干净新目录，审阅 diff、变更记录和依赖变化。不要以 root 运行，不执行不明来源安装器
3. 在新目录运行全部测试与 `--check-config`。配置校验不会启动 Codex 或网络服务
4. 当前版本会拒绝未知配置字段、重复键、非布尔 enabled、相对路径、符号链接项目根、敏感根，以及与 Codex home 重叠的项目；升级时逐项核对配置
5. 在变更窗口停止旧前台隧道实例，明确更新 profile 中的源码路径，保持私有配置与最小权限不变
6. 启动一个新实例；依次验收 list_projects、list_files、read_file，以及按需 read_thread 分页。确认工具列表是所选版本预期的只读集合（0.3.0 为八项）
7. 若失败，停止新进程，把启动命令/profile 路径指回原目录，再启动一个旧实例。不要同时运行同一 tunnel ID 的两份 stdio 服务

本项目不自动迁移配置、不重写原始 Codex 会话、不修改隧道权限。回退不会撤回已经被客户端读取的数据。若发现敏感内容共享或密钥泄漏，应先停止连接并撤销相关权限，再处理代码版本。

当前源码标识为 0.3.0 候选，尚未创建正式发布标签；维护者应在 CHANGELOG 中清晰记录后续版本和兼容性变化。


## 0.2.x → 0.3.0

- 原有 `--transport stdio`、`--transport http`、`/v1/call`、配置字段和六个工具的参数/结果保持兼容
- 新增 `workspace_info` 与 `project_overview`，因此工具总数由六变八；使用固定数量断言的客户端需更新，未增加写入或命令能力
- 通用工具实现移到 `bridge.workspace`，原 `bridge.server.Bridge` 导入仍兼容；Codex 适配仍独立在 `bridge.history`
- 只有新 `--transport streamable-http` 需要安装 `.[http]`：官方 MCP v1.30+（<2）及 Uvicorn 0.52.1+（<0.53）和其传递依赖。安装前审阅依赖，使用独立虚拟环境
- 旧 stdio 的 2024-11-05 协商不变；新 HTTP 是明确的 2025 版本矩阵，两条路径不可混淆。2026 新协议与 SDK v2 不是此升级的一部分
- 没有自动迁移、自动生成 token、权限扩大、会话导入或网络部署。重新验收后再由操作者决定是否切换
